# Security headers and CSP

Status of what is implemented against what is planned. Design source: section 5 of `docs/audit/plans/E20-plan-draft.md`.

## Implemented in the Phase 0 PR

### Marketing (`apps/marketing/server.ts`, `server/security.ts`)

- `Strict-Transport-Security: max-age=31536000; includeSubDomains` (no preload, decision D8).
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
- Enforced `Content-Security-Policy`. In production `script-src` is `'self'` plus a per-request nonce (no `https:`) and `connect-src` is `'self'` (no `https:`, no `ws:`); the marketing site makes no cross-origin fetches. Development keeps `'unsafe-inline'`, `'unsafe-eval'`, `https:` and `ws:` for Vite HMR.
- 500 responses return a generic body; the error is logged server-side only.
- The app URL is resolved once at boot from `VITE_APP_URL`, then `APP_URL`, then the environment (never the request `Host` header).
- `/.well-known/security.txt` is served as `text/plain` only when the `SECURITY_CONTACT` env var is set on the marketing service (email, `mailto:` or https URL); otherwise it returns 404. `Expires` is computed per request (now + 1 year).

### Backend (Q4, separate task in the same PR)

`helmet` configured for a JSON API (CSP `default-src 'none'`, HSTS, nosniff, `Referrer-Policy: no-referrer`), explicit body limits, CORS from `CORS_ALLOWED_ORIGINS`.

### MCP transport (Q10)

Generic 400 bodies for non-auth errors, `WWW-Authenticate` on 401, `Retry-After` on 429, and a per-IP limiter for failed authentication (10 per minute).

## Web caching and response-header coverage

`apps/web/app/security/middleware.server.ts` applies `applyCachePolicy` (in `headers.server.ts`) to every document, `.data` and resource-route response. There is no public-cacheable allow-list: the root loader returns the user, profile and access token for every route (including `/tools`) and may append a refreshed session `Set-Cookie`, so every HTML and `.data` response is user-specific.

- Default is `Cache-Control: no-store` plus `Pragma: no-cache`.
- A response that sets a cookie is always `no-store`.
- A route's own `Cache-Control` is kept only if it already contains `no-store` or `private`; a weaker value (`public`, `max-age`, ...) is replaced with `no-store`.
- Anything not `no-store` (a kept `private`) gets `Vary: Cookie`, keeping existing `Vary` values.
- A future cacheable public page needs an explicit, reviewed opt-in (a route that loads no user data plus a change to this policy), never an implicit default.

### Web server (`apps/web/server.ts`)

The web app runs on a small custom Express server (`@react-router/express`, a near-verbatim port of `react-router-serve` 7.18.5) instead of `react-router-serve`. It exists so the response headers cover every response, including those React Router builds outside any hook: the document-request CSRF 400, document-level catch 500s, `/__manifest` responses, and static files from `express.static`.

- `apps/web/server/securityHeaders.ts` is the first middleware. It sets the whole `SECURITY_HEADERS` set (imported from `app/security/headers.server.ts`, the single source) plus `frame-ancestors 'none'` on every response. When React Router appends one of those headers itself, the app's value replaces the default instead of being appended next to it (the report-only CSP below is a different header name, so it is simply added once next to the enforced one); a header written through `res.writeHead(status, { ... })` overrides the default too (Node merges that object over `setHeader` values).
- `app.disable("x-powered-by")`.
- `trust proxy` is hard-coded to `1` (Railway terminates TLS one hop in front), so `req.ip`, `req.protocol` and the forwarded host come from the last proxy hop. A `TRUST_PROXY_HOPS` variable for a second hop (for example a CDN in front of Railway at the custom-domain cutover, the HOLD item) is not wired yet; until it is, adding a hop in front of the app means editing `server/app.ts`. A wrong hop count lets a client spoof `X-Forwarded-*`. CSRF origin checks read `x-forwarded-host` and `x-forwarded-proto` directly and do not depend on this setting.
- Request ids (`x-request-id`) are client-suppliable (a UUID, or a strict-charset `x-railway-request-id`). They are for log correlation only, never for authorisation, idempotency or deduplication.
- `source-map-support`, which `react-router-serve` installed, is not carried over. The web build emits no `.map` files (it never mapped anything), so production stack traces are the same as before; Sentry has its own source-map upload path if that is wanted later. Under Bun, stack traces are the bundled `build/server/index.js` positions.
- `Cache-Control` for documents stays with `applyCachePolicy`. Static files keep exactly the values `react-router-serve` used: `/assets` `public, max-age=31536000, immutable`, everything else in `public/` and `build/client` the `express.static` defaults and a 1 hour `max-age` for `public/`. The `compression` middleware is unchanged.
- Shutdown: SIGTERM and SIGINT stop accepting connections, let in-flight requests finish and exit 0; a drain that exceeds 14 seconds is forced to exit 1 (Railway drains for 15 seconds, `apps/web/railway.json`).
- The access log is described in `docs/security/logging-policy.md`.

`.data` responses are still also covered through `handleDataRequest` in `entry.server.tsx`. Tests: unit tests in `apps/web/server/*.test.ts`, and `apps/web/server/server.integration.test.ts`, which spawns the built server and checks the headers on every response kind (CI: the E2E smoke job runs `bun run --cwd apps/web test:server` after the build). Rollback: redeploy the previous deployment, or restore the previous start command (`react-router-serve ./build/server/index.js`) in `apps/web/Dockerfile` (`CMD`) and `apps/web/package.json` (`start`); `@react-router/serve` stays installed for one release.

`Cross-Origin-Resource-Policy: same-origin` is sent with the other headers: nothing cross-origin embeds the app's documents (the marketing site only links to it; Sentry and WorkOS are outbound).

ZAP baseline (`.zap/rules.tsv`): rule 90004 is ignored only for the missing COEP, which would block third-party resources for no isolation benefit we use; the web app sends COOP and CORP. The marketing site does not send COOP or CORP yet, which the ignore also hides for that target. Rule 10049 (storable and cacheable content) stays at the default WARN: the cache policy above is the real control, and a remaining finding points at a response worth checking (static assets are expected to be cacheable). The CSP wildcard finding (10055) stays visible and is not ignored: `.zap/rules.tsv` has no row for it on purpose. In the report-only policy the wildcard is `img-src ... https:` (any HTTPS image host, kept for avatars and receipt previews); ZAP may also flag `style-src 'unsafe-inline'`. Both are deliberate for now and are revisited when the policy is enforced (E20-N12).

## Web CSP, report-only (E20-N11, implemented)

The web app sends a SECOND header, `Content-Security-Policy-Report-Only`, on every HTML document response, next to the unchanged enforced `Content-Security-Policy: frame-ancestors 'none'`. It enforces nothing: browsers only POST violations to `/csp-report`. The code is `apps/web/app/security/csp.server.ts` (policy builder, nonce generator) and the root middleware (`middleware.server.ts`), which sets it only on `text/html` responses (not `.data`, resource routes, static files, or the CSRF 403).

| Directive         | Value                                                                                                                                                                                                                                                          |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `default-src`     | `'self'`                                                                                                                                                                                                                                                       |
| `script-src`      | `'self' 'nonce-<N>'` (per-request 128-bit nonce, no `'unsafe-inline'`, no `'unsafe-eval'`)                                                                                                                                                                     |
| `style-src`       | `'self' 'unsafe-inline'` (inline styles in `root.tsx` and components; Radix injects style elements)                                                                                                                                                            |
| `img-src`         | `'self' data: blob: https:` (the `https:` is the ZAP 10055 wildcard)                                                                                                                                                                                           |
| `font-src`        | `'self'` (fonts are self-hosted, D11, and always emitted as hashed files under `/assets`, never inlined as `data:`)                                                                                                                                            |
| `connect-src`     | `'self'` plus the exact Sentry ingest origin taken from `SENTRY_DSN` (scheme and host only, e.g. `https://o123.ingest.de.sentry.io`, https only); no wildcard, and no entry at all when the DSN is unset or invalid                                            |
| `form-action`     | `'self'` plus the exact WorkOS origin (`https://api.workos.com`, or `https://$WORKOS_API_HOSTNAME`) and the marketing origin (`getMarketingUrl`, so `VITE_MARKETING_URL`); the logout form posts to `/logout`, which redirects to WorkOS and then to marketing |
| `frame-ancestors` | `'none'`                                                                                                                                                                                                                                                       |
| `object-src`      | `'none'`                                                                                                                                                                                                                                                       |
| `base-uri`        | `'none'`                                                                                                                                                                                                                                                       |
| `report-uri`      | `/csp-report`                                                                                                                                                                                                                                                  |

Nonce flow: the root middleware generates the nonce (`crypto.randomBytes(16)`, base64url) and stores it in the router context (`nonceContext`); `entry.server.tsx` reads it from `loadContext`, wraps the render in `NonceProvider` (`app/security/nonce.tsx`) and passes it to `renderToPipeableStream` and `<ServerRouter nonce>`. `root.tsx` puts it on the `window.ENV` script, the theme-init script, `ScrollRestoration` and `Scripts`, in both the app and the root `ErrorBoundary`. Hydration: the client provides the same nonce, read back from the DOM `.nonce` property of the first nonce-bearing script (`readNonceFromDom`, see "Known limits" below for why `""` is wrong). Any new inline `<script>` must use `useNonce()`; the SSR test `entry.server.nonce.test.tsx` fails if a script in the root document has no nonce.

`/csp-report` (`app/routes/csp-report.ts`, logic in `app/security/csp-report.server.ts`): accepts POST bodies of type `application/csp-report`, `application/reports+json` and any other JSON; no session needed. Always 204 (invalid JSON, wrong shape and rate-limited requests included), except 413 for a body over 8 kB. In-memory limit of 60 reports per minute per client plus a per-process cap of 600 per minute across all keys (excess is answered 204 and not logged, so rotating the key cannot multiply log lines), keyed by the last `X-Forwarded-For` entry (the one the single trusted Railway hop appended; same trust model as `trust proxy` 1), resetting on deploy. It logs one JSON line per report with only the directive name, the blocked origin (scheme and host, or a keyword such as `inline`) and the document path without query or fragment, with opaque path segments collapsed to `:id`, all through `redactString`. The raw report, `script-sample`, `original-policy` and every query value are never logged. It is not exempt from the E20-N1 same-origin check: browsers send CSP report POSTs with `Origin` and `Sec-Fetch-Site: same-origin` for a same-origin `report-uri`, so a real report passes, and a cross-site POST gets the 403 like any other write.

Reading reports: filter Railway logs on `"context":"CspReport"`.

Known limits of the soak (read before E20-N12):

- Responses React Router builds outside the middleware (the document CSRF 400, document-level 500s, `/__manifest`) and static files carry no report-only CSP and no nonce. That is fine while report-only. They contain no inline scripts, so an enforced policy would not break them, but N12 needs a plan for them: see "Responses outside the middleware: plan for N12" below (a restrictive non-document default is already implemented for the safe classes).
- Chromium sends report POSTs with `Origin` and `Sec-Fetch-Site: same-origin` (verified with Playwright). Safari and Firefox may omit `Origin` or `Sec-Fetch-Site` on report POSTs, in which case the E20-N1 check answers 403 and the report is lost. The soak evidence is therefore effectively Chromium-only. A narrow `/csp-report` exemption is the fallback if evidence from other browsers matters.
- Hydration and the nonce (resolved, follow-up PR `fix/csp-followups-hydration-font-n12`): React 19 compares a hydrating element's `nonce` against the DOM `.nonce` property (react-dom development source: `node.nonce` in `getValueForAttributeOnCustomComponent` and in the `diffHydratedProperties` path), which keeps the real value in EVERY browser even when the attribute itself reads back as `""` (Chromium with an enforced policy, Firefox). With only the report-only policy Chromium also exposes the attribute. So a client that renders `nonce=""` against a server that rendered the real nonce logs a development-only "attributes of the server rendered HTML didn't match" error, in all browsers and with either policy mode; production React never checks attributes, so it was never a production hydration failure, and it is NOT React error #418 (text content). The client now renders the same value the server did: `entry.client.tsx` wraps the app in `NonceProvider nonce={readNonceFromDom()}` (the `.nonce` property of the first nonce-bearing script), so no `suppressHydrationWarning` is needed (and could not be added to React Router's own `Scripts`/`ScrollRestoration`). The one remaining development-only nonce diff is on React Router's critical-CSS `<style>` tags in `Links` (server `nonce=""`, client `undefined`), which is React Router internals, dev only.
- React error #418 on `/tools` and `/sandbox` (fixed in the same PR). Root cause: the shared shell (Header, footer) uses the `common` i18n namespace, but only four routes declared `handle.i18n`. remix-i18next picks the namespaces to preload from route `handle`s on both the server (`getRouteNamespaces`) and the client (`getInitialNamespaces`); on routes without a handle the namespace list is empty, so the server (synchronous `i18next-fs-backend`) rendered the nav link "Home" while the client (asynchronous `i18next-http-backend`) rendered the key `home` first and fetched `/locales/en/common.json` only after hydration. Evidence: a development-mode run in Chromium printed `+ home` / `- Home` on the `Header` nav link, and `common.json` was requested only on those two routes. Fix: `export const handle = { i18n: ["common"] }` in `root.tsx`. Regression test: `app/hydration.test.tsx` (real development React, server markup hydrated on a client with an async backend; a client with no preloaded namespace is the positive control and fails it).
- Firefox/Safari: Playwright Firefox is NOT installed on the development machine (only Chromium build 1254) and was not downloaded (browser binaries need the owner's approval), so no Firefox run was done. Manual check: in Firefox, open `/tools` and `/sandbox` on a development build (`bun run dev` with WorkOS dummy env) and confirm the console has no "Hydration failed" and no "attributes of the server rendered HTML didn't match" message naming `nonce`; on a production build confirm no minified React error 418/419/423 in the console. Compare with `main`, where the 418 appears.

- `font-src` and the `data:` font (resolved): Vite inlined the one `@fontsource-variable` woff2 file under its 4 kB default `assetsInlineLimit` (a `data:font/woff2;base64` URL in `build/client/assets/root-*.css`), which `font-src 'self'` flags. `apps/web/vite.config.mts` now sets `build.assetsInlineLimit` to a function that returns `false` for `.woff`, `.woff2`, `.ttf`, `.otf` and `.eot` (and `undefined`, the default, for everything else). Before: 10 font files plus 1 inlined `data:font/woff2` in the root CSS; after: 11 `.woff2` files under `build/client/assets/` (served immutable for a year by the custom server) and no `data:font` or `data:application` string anywhere in `build/client`. `data:` is NOT in `font-src`. No preload hack was added. Storybook imports the same `@repo/ui/fonts.css` and the same Vite config, so it simply loads real font files.

### Responses outside the middleware: plan for N12

Which responses never reach `securityMiddleware`, and so never get the app's nonce CSP: the document-level CSRF 400 (React Router rejects before middleware), document-level catch 500s, `/__manifest`, everything `express.static` serves (`/assets`, `build/client`, `public/`), and `res` bodies written by Express itself (finalhandler). `/healthz`, `/login`, `/logout`, `/csp-report`, `.data` and every other route (the dev-session `/login` and `/logout` included) DO run the middleware and carry the app's own headers. `server/securityHeaders.ts` stamps the 8 `SECURITY_HEADERS` (enforced `Content-Security-Policy: frame-ancestors 'none'` among them) on every response before anything runs, and the app's first `res.append` of a default header replaces it.

Exact semantics (verified in `server/securityHeaders.test.ts` and `server/app.test.ts`): the app's CSP replaces the default when it is appended, `setHeader`ed or passed to `writeHead`; a response the app never touches keeps the default; the report-only header is a different name and is added once. So after N12 flips `FULL_CSP_HEADER_NAME`, a document has exactly ONE `Content-Security-Policy` (the app's full nonce policy, which carries `frame-ancestors 'none'` itself) and responses outside the middleware keep a default.

Implemented in this PR (the safe part): `server/securityHeaders.ts` replaces the `frame-ancestors`-only default with `NON_DOCUMENT_CSP` = `default-src 'none'; frame-ancestors 'none'; base-uri 'none'` (from `app/security/headers.server.ts`; NOT in `SECURITY_HEADERS`, so the E2E assertion `content-security-policy` equals `frame-ancestors 'none'` on documents, and the Docker smoke grep on `/healthz`, are untouched) at header-flush time, only when ALL hold: the app did not give a CSP (still pending, value still the default, none in `writeHead`'s header object, no raw header array) and the type is JSON, `text/plain`, `text/css` or `font/*`, or the type is missing AND the status is >= 400. Every other response, HTML, JS, SVG, XML, PDF, images, 204, 304, redirects, keeps the default. Because it keys off the Content-Type of a response the app did not give a CSP, it cannot touch an HTML document (an app document always has its own header, and `text/html` is excluded anyway) and it cannot touch subresource loading (a CSP on a CSS, font or JSON response does not restrict the page that loads it). Proof: `server/securityHeaders.test.ts` (allow-list, writeHead, setHeader, append, 204, 304, 400 without type), `server/app.test.ts` (real `createApp` over a tmp static dir and the real React Router handler: JSON, CSS, font, text, CSRF 400 carry it once; JS, SVG, HTML, image, 304 do not; an HTML document with the app's own CSP keeps exactly that header once plus the report-only one), and `server/server.integration.test.ts` against the built server (`/__manifest` JSON, CSRF 400, hashed font, `/healthz`, a document). Browser check (Chromium, built server): `/tools` and `/sandbox` with the restrictive responses in place show no console CSP messages and no `/csp-report` lines; a deliberate `data:` font is reported as `font-src` (positive control).

Risks. (1) A default CSP on a response that is really a document: not applicable while the allow-list holds; the SVG/HTML/XML class is deliberately excluded. (2) Workers and Service Workers: none exist; JS is excluded so a future worker is not broken. (3) Source maps: the web build emits none. (4) Storybook: separate dev server, never behind this Express server. (5) Cross-origin embedding: `Cross-Origin-Resource-Policy: same-origin` already blocks it; the policy adds `frame-ancestors 'none'`, which the default already had. (6) A future route that sets its own CSP only through `res.set` after the first byte: not possible, headers are flushed once.

N12 order. 1) Land and soak this PR (restrictive default is already enforced; it cannot affect pages). 2) On staging set `CSP_ENFORCE=true` (the one-line change in `csp.server.ts`: `FULL_CSP_HEADER_NAME = process.env.CSP_ENFORCE === "true" ? "Content-Security-Policy" : "Content-Security-Policy-Report-Only"`; the full policy already contains `frame-ancestors 'none'`, so the enforced default stops being a second `Content-Security-Policy` header: the app's value must REPLACE the default through the same set-if-absent rule, which is why the full CSP must go through `res.append` like every other header, and an integration test must assert exactly one `Content-Security-Policy` header on a document, whose value starts with `default-src 'self'`). 3) Acceptance tests to add first: every document class (`/sandbox`, `/tools`, an error document, the root ErrorBoundary) has exactly one enforced `Content-Security-Policy` whose script-src nonce matches its inline scripts and no report-only header (or the report-only copy of any stricter later policy); `/healthz` and the E2E spec's `content-security-policy` expectation are rewritten from "equals `frame-ancestors 'none'`" to "contains `frame-ancestors 'none'`" in the same commit that flips the flag; the non-document table above stays as tests; `.data` and resource responses keep `frame-ancestors 'none'`. 4) Manual journey on staging (sign-in, budget add, tax add with receipt, profile) with the browser console clean. 5) Production. Rollback: unset `CSP_ENFORCE` (back to report-only; the enforced `frame-ancestors` header returns on its own through `SECURITY_HEADERS`) or redeploy the previous deployment. Revert of the restrictive default alone: delete the `writeHead` hook in `server/securityHeaders.ts`; nothing else depends on it.
